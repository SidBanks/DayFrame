## Adjacent Proposal boundary and domain coverage

`proposalWriteLifecycle.test.ts` drives every ordinary common-writer alias while a leased write is held: record, shown, supersede, candidate, accept, modify-and-accept, reject option, reject Proposal, and desired retry. The rejected commands do not queue a candidate. Abort preserves exact desired retry; changed desired origin/source rejects; uncertainty protects and suppresses automatic handoff. Full-image comparison preserves prior records and rejects incorrect readback. Direct owner clear is refused during physical work; attached runtime installation and stale/private capability misuse are tested by `acceptanceCoordinator`.

`acceptanceReplacementIsolation` adds the separately demonstrated earlier Proposal-persistence × clear/V14 orderings, with the same counted gate and exact restart assertions. `acceptanceSourceWitness` records an unrelated valid offer through the real Proposal writer while realization is held, and verifies the immutable accepted target remains usable. The fixture's offer is derived through the canonical domain function; the test concerns writer coexistence, not current UI offer eligibility.

Three-role fault fixtures derive actual Goal/Demand/footprint/Sleep allocation and acceptance through owners. Adjacent-day and compatible-buffer tests additionally use complete validated domain footprints with explicit support/protection relationships. Retained realization, capacity, Proposal, accepted evidence, V14, older backup, publication, Structure, Sleep, Goal/G1/G2 and Progress suites remain part of the full run. No durable domain validator or scheduling conflict rule was changed.

## Counting and proof boundaries

At each original replacement gate the permanent assertion is **one attempted selected mutation, zero created transactions**; first replacement is busy with unchanged epoch; after release **one selected transaction** completes. A fresh explicit replacement then performs its own documented writes. Counts are owner-operation counts, not all database activity in fixture setup.

The never-terminal test supplies an intentionally unresolved synthetic terminal receipt to prove nonrelease; it does not claim a browser naturally produces that condition. Other physical certainty fixtures delegate to the real storage adapter and `fake-indexeddb`; browser fault cases use actual Chromium IndexedDB with labeled delivery suppression. No broad “busy or success” expectation replaces a phase-selected assertion.
