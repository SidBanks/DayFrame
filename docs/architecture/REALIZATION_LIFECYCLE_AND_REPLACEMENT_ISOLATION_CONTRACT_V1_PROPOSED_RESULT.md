# Realization Lifecycle & Replacement Isolation Contract V1

**PROPOSED — AWAITING ARCHITECTURAL ACCEPTANCE — NOT IMPLEMENTED**

Task 9.29.3 recommends this single contract. It neither adopts architecture nor authorizes application changes. Task 9.29 remains PARTIAL/BLOCKED. The accepted publication and Structure repairs remain unchanged.

## 1. Decision, scope and evidence

Use **one nonqueued execution lease per realization owner**, original-lifetime tokens, and the existing shared before-snapshot replacement controller. A second overlapping realization command returns explicit busy, including a duplicate for the same acceptance. It does not join, queue or replay. An already-settled, completely verified current realization returns `alreadyRealized`. Use the existing storage admission callback and native terminal observer; add complete-set readback before adoption. Release only after physical terminal and owner settlement. Waiting for module/preparatory reads holds no lease and confers no right to run later in a different lifetime.

Keep Proposal acceptance and realization as two durable transactions. Bind their automatic handoff to the lifetime captured before acceptance's first await. **Also fence the existing Proposal owner commit boundary**: source inspection and new diagnostics establish an independent earlier Proposal-persistence gap, not just a delayed realization. A realization-only patch cannot make the end-to-end acceptance chain safe. Section 4 specifies this necessary adjacent part of the one proposed repair slice; §14 lists it separately from the original finding.

Guarantee: one live, registered store/Proposal/realization composition and its participating adapters. Independent readers may reopen after settlement. This is not cross-tab, arbitrary raw writes, multiple active stores, process/device, global locking or all-owner safety. It introduces no new journal, database, durable operation ledger or scheduling policy.

Evidence in `docs/implementation/phase-9/evidence/task-9.29.3/`: the unchanged copied five-case diagnostic reproduces automatic/retry × clear/V14 and a healthy control. Additional isolated tests demonstrate acceptance persistence resuming after clear/V14, two physical realization transactions for automatic plus same-acceptance retry, and healthy canonical productive/support/protection realization. No native failure prevalence or affected-user classification is inferred.

## 2. Preserved domain boundaries

1. ProposalDecision and complete Accepted Allocation commit first. Realization plus **all** productive/support/protection facts commit separately and atomically. Failure/conflict does not erase acceptance; explicit later replacement may remove it.
2. Never accept again to retry realization, compensate with a rejection, widen scope, move/replan accepted geometry, regenerate claims from today's footprint definition, or introduce partial/per-role persistence.
3. Retain `accepted-allocation-realization@1`, deterministic realization ID from acceptance ID/revision, deterministic role/claim fact IDs, exact half-open geometry, canonical owner days, lineage, required support and Buffer semantics. Buffer remains protection, not executable activity. No Progress or publication is implicit.
4. Accepted Allocation V1/incomplete footprints stay inspectable but inapplicable. Do not upgrade them or infer missing support. A current immutable complete V2 is the scheduling target.
5. Acceptance remains distinct from scheduling success and from currentness. An outer accepted result can truthfully describe an earlier committed operation even if a later explicit clear removed it. It must not be presented as current acceptance or current scheduling success after replacement.

## 3. Runtime identity and entry

Illustrative spelling below is normative in semantics; implementation may use existing typed helpers without persisting these objects:

```ts
type RealizationOrigin = Readonly<{
  owner: object; // exact registered realization owner
  operation: object; // unique attempt, not accepted ID
  authorityEpoch: number;
  realizationGeneration: number;
  proposalOwner: object;
  proposalGeneration: number;
  acceptedAllocationId: string;
}>;
type AcceptanceOrigin = Readonly<{
  proposalOwner: object;
  operation: object;
  authorityEpoch: number;
  proposalGeneration: number;
  realizationOwner: object;
  realizationGeneration: number;
}>;
type OperationReceipt = Readonly<{ isCurrent(): boolean }>;
```

Owners recognize issued identities, not a structurally similar caller object. Capture/freeze Proposal input or retry ID synchronously at the public/lazy façade, before any module import/await. The lazy façade has an owner-stable identity/generation shell even when its module is unloaded. Factory commands capture at their own entry when not passed a valid private upstream origin. Do not expose token construction, coordinator capabilities or private handoff entry to UI.

Automatic realization derives an attempt from the **original acceptance origin** plus the exact accepted ID/revision/decisive payload produced by its verified commit. It may allocate a new opaque attempt identity, but may not sample a new epoch or generations. Validate before callback dispatch and again on owner entry/after lazy loading. If replacement or abort happened meanwhile, do not resolve matching replacement data to rescue the old handoff. Identical restored IDs/bytes do not renew intent.

Fresh explicit retry captures a genuinely new origin and resolves the acceptance currently present. It is allowed to inspect identical restored authority, but it still must meet current admission, completeness, foundation/occupancy and durable-idempotence checks.

Advance owner generation on runtime installation, successful owner clear/replacement and abort restoration. A begun replacement advances shared epoch before snapshots even if capture fails; never roll epoch/generations back with data. Ordinary successful append does not invalidate all earlier result receipts; ordinary content/source revision is a separate witness. No token, lease, counter, attempt or receipt enters snapshots, backups, staging, journal or records.

## 4. Acceptance persistence and automatic handoff

### 4.1 Earlier, independent boundary

Current `proposalSurface.commit` persists a whole Proposal authority image (clear plus puts), then installs its precomputed array. New tests pause that acceptance write after revalidation and before the real adapter. Clear/V14 succeeds; releasing it recreates accepted authority. This is independently demonstrated and must be addressed explicitly, rather than treating “acceptance committed” as true for every in-flight call.

Select a **Proposal-owner nonqueued write lease**, independent of the realization lease, around each ordinary common commit/persistence route. This is lifecycle serialization, not new decision semantics. Cover record/lifecycle/reject/stale-transition/accept/candidate writes and explicit exact desired-envelope retry because they share the same whole-image writer. Do not leave an alternate common-writer route able to install an old array. Direct owner clear/replacement belongs to §9's replacement route, not ordinary persistence.

Capture origin before lazy/revalidation. Asynchronous revalidation is preparatory and replaceable. Before constructing the final candidate from current authority, acquire the Proposal lease synchronously; another unresolved Proposal write returns `proposalBusy`, no queued replay. Recheck exact current Proposal/option/candidate, current semantic witness, immutable lineage, accepted-claim conflicts and the existing actual-acceptance-time Structure rules. Preserve their existing single captured time; do not add a clock policy. Derive the whole candidate from the current leased base and remember its base revision/identity. No ID allocation or new accepted intent occurs just to service a persistence retry.

Hold that lease through physical admission, native terminal, complete authoritative-image verification, installation of authority/desired/durability, and matching synchronous notifications. Admission checks original owner/epoch/generation, exact lease/base, ordinary readiness, attempt-open flag and the captured source witness. Use the same terminal/uncertainty rules as §7, not the old Boolean `persist` collapse. Verify all intended Proposal records by canonical composite key including record type/revision, exact count and nested content; preserve supported record interpretation. Uncertainty protects the Proposal owner and blocks automatic realization/ordinary replay of its `desired` image. Known atomic abort retains the existing exact desired retry contract under its originating lifetime; successful replacement discards it, and abort-restored desired data needs a fresh explicit retry.

This addition is proposed explicitly as an adjacent dependency, not as a repair already authorized or implied by 9.29.2. No Proposal option, ranking, modification, acceptance-conflict, time, schema or authority semantics change.

### 4.2 Handoff order

On verified acceptance: record the outer accepted evidence and its receipt while the Proposal lease is current, then release the Proposal lease **before** entering realization. Never wait for realization while holding the Proposal lease. Dispatch exactly one automatic attempt with the original handoff origin. A replacement can win in this interval; then the inner result is `rejected/contextReplaced`, zero realization writes, and the outer result still describes the earlier acceptance with a noncurrent receipt. No reaccept, timer or background retry occurs.

If another realization is executing, the inner attempt returns `rejected/realizationBusy`; the current acceptance remains intact and explicit retry is available after the other operation settles. A known acceptance persistence failure does not dispatch realization. Unconfirmed acceptance does not dispatch it even if a terminal event suggests commit. A later fresh explicit retry requires independently established current accepted authority and ordinary readiness.

The two leases are never nested while awaiting each other. An ordinary Proposal append can coexist with realization of a different existing acceptance: ordinary decisions preserve existing accepted snapshots, while destructive Proposal replacement uses the shared controller and cannot cross a realization lease. Admission compares the **exact target acceptance**, not unrelated Proposal history bytes, so a harmless new offer is not interpreted as missing lineage.

## 6. Same-owner concurrency and source witness

### 6.1 No queue, no joining

The current owner has no serialization contract: two same-acceptance attempts can both pass the runtime lookup, create two transactions, and each report realization. Distinct attempts each build an authority array from their original base; deterministic IDs do not prevent lost runtime entries. Choose rejection, not publication's FIFO policy.

A second attempt submitted after A acquires the lease always returns `rejected/realizationBusy`, whether it is automatic or explicit and whether it names the same or a different allocation. It does not validate against A's tentative state, report `alreadyRealized`, hold an exclusion of its own, or wait. Preparatory calls may be in flight without a lease: the first to reach execution admission wins; any other reaching admission before release rejects. There is no promised submission-order queue.

After A settles, a **new** same-ID call returns verified `alreadyRealized`; a new distinct-ID call rechecks the now-current full facts. Nonoverlapping valid claims realize; overlapping activity/protection produces `conflicted/scheduleConflict`; compatible Buffer/Buffer remains permitted. A previously busy call is not silently replayed. Replacement between calls invalidates pre-existing preparatory tokens. No precomputed waiting candidate survives.

### 6.2 Source validity is separate from lifetime

Capture a synchronous exact witness of the target accepted ID/revision/payload, realization base, current saved setup (including Work, fixed/manual facts and canonical User Day configuration), Sleep requirements/accepted placements, relevant PlanDecisions, Composition occupancy and current realized facts/readiness. A content fingerprint must preserve canonical semantic fields; array position, title or geometry alone cannot substitute for identity/incarnation. Compare the current target and relevant sources immediately before native transaction creation. Conservatively invalidating on a saved-source change is allowed; treating a changed source as equal merely because epoch is unchanged is not.

Reuse existing `deriveFoundationalSchedule` / `captureSleepAuthority` and current canonical occupancy adapters, with the same captured operation instant, to obtain a read-only current foundation and Work/manual/fixed/Sleep/realized occupancy snapshot. The current `currentSchedule` wiring reads Preview blocks; it is **not sufficient as a freshness witness by itself** when saved state has changed or Preview is absent/stale. Compose existing canonical generated Work/scheduled/hard-occupancy evidence, preserve source/role IDs, deduplicate the same subject by identity, and include complete current realized facts. This is read-only canonical derivation, not the UI Generate command, new scheduling policy, Capacity-as-authority, or movement of accepted claims. No new stateful engine or UI Preview write is authorized.

If existing canonical sources cannot establish current complete evidence, return `inapplicable/sourceUnavailable`, no write. Before physical admission, source mismatch returns `rejected/sourceChanged`, no write and no automatic recomputation/resubmission. A fresh explicit command obtains current truth: Sleep foundation review, schedule conflict or exact lawful realization. It never moves or shrinks accepted geometry.

The no-await admission predicate performs pure owner/witness comparisons; it does not call user code, sample a new planning clock, invoke commands or await derivation. All inputs for the comparison have synchronous current-owner access. The adapter's internal nonthrowing observer may register terminal evidence but must not author or replace state.

Admission is the linearization point for validity of a **new** physical realization attempt. Later lawful authoring after transaction creation is a later operation; it may make the schedule need review but does not retroactively cancel the admitted write or permit a compensating delete. Verification establishes exact stored authority, not eternal conflict freedom. If sources changed after admission, success includes runtime `reviewRequired: true`; consumers requery canonical evidence and must not claim the period remains ready. Ordinary authoring policies are unchanged. Whole-authority replacement remains excluded for the entire lease.

## 7. Physical terminal, certainty and complete-set verification

Use the existing optional `mutate(rows, admit, observe)` infrastructure. The admit predicate checks exact registered owner, original epoch and both owner generations, active lease identity, attempt-open flag, current ordinary readiness/protection, unchanged exact acceptance/base and the §6 source witness. A false result creates no transaction. Wrappers preserve all arguments. The observer registers after native terminal handlers exist and before requests. Request errors or transaction `error` notifications alone are not terminal. Enqueue errors abort and await actual abort/complete.

Close attempt admission on returned failure or thrown/lost acknowledgment. If a wrapper throws before registering a transaction, later delegation of that same attempt is denied by its closed callback. If a receipt exists, keep the exclusion until its actual terminal promise settles. A timeout or database-close request does not prove cancellation. Reuse the accepted native-terminal → MessageChannel acknowledgment-delivery checkpoint for a permanently missing outward promise, without changing publication's mechanism. A normal promise can drain before that checkpoint; absence becomes uncertain, not verified success. No receipt plus a forever-pending outward call remains fenced/unconfirmed; there is no evidence to infer it never started. If a receipt never terminates, remain physically nonquiescent and expose “scheduling outcome unconfirmed; operation still finishing,” not an ordinary retry or destructive replacement.

For a normal acknowledged successful commit, perform durable readback under the lease:

- Resolve the exact current accepted snapshot and deterministic realization ID.
- Read the saved realization and every owned fact, and ensure there are no missing, duplicate or extra facts for that realization/acceptance. Check all three ID lists, accepted-claim membership, role mapping, lineage, exact geometry, canonical days, and full candidate record/fact bytes including the attempt's `realizedAt`.
- Reuse pure staging/identity validators with the immutable accepted footprint to reconstruct expected facts, without treating the newly saved facts as conflicts against themselves. Check complete membership, not just a subset of listed IDs.
- Verify the settled base is unchanged; retain every earlier verified realization/fact. With a single lease and replacement excluded, a base mismatch is an invariant/protection failure, never permission to install the precomputed whole array.
- Install only the verified union of current settled base and the exact verified new set. All owned rows are one atomic unit. No per-role success, partial overlay or blind merge of unverified storage is allowed.

`alreadyRealized` must similarly establish the current stored complete set against the original stored timestamp and current immutable acceptance, after lifetime validation. It does not restage new geometry/time or reapply today's foundation as a retroactive veto of already-accepted scheduled reality. Current conflicts may require Review, but do not erase or duplicate existing realized facts. Startup-qualified cache may guide lookup; this selected contract requires readback before command-level already-realized success.

A known adapter atomic abort yields known no new writes; retain acceptance and prior authority, release after terminal/classification and allow fresh explicit retry. A caught exception with no registered receipt closes admission; under the required synchronous observer contract, no transaction has started and later delegation cannot start one, so return known pre-write `failed/atomicPersistenceFailure`. A registered native abort also proves no new complete set and returns that safely retryable failure, even if outward acknowledgment was lost. A registered commit with a thrown/lost acknowledgment remains **unconfirmed**: physical completion alone is not verified command success. These are realization-specific certainty choices; publication's accepted classifications remain unchanged. An acknowledged commit with failed/inconsistent readback yields `verificationFailedAfterCommit`. Both protect realization, retain exact attempt/raw evidence when readable, and disallow ordinary retry. They do not install unverified candidate facts. If evidence read fails, record unavailable evidence and finish that classification; do not silently label empty history. A genuinely unresolved evidence/terminal promise retains exclusion rather than claiming settlement.

Release the lease only when: any created transaction is terminal; admission is closed; verification or failure classification has completed; runtime/metadata/protection disposition and evidence capture are settled; result recording and synchronous notifications have run under the matching origin. Terminal uncertainty then becomes **quiescent protected**, not permanent busy. Protection persists until supported existing recovery/reload establishes authority; this proposal adds no unlock, orphan deletion or repair action. Synchronous notification exceptions are caught and conservatively classified before lawful release; they never cause another write or poison a future independent command.

## 9. Coordinator and replacement routes

Extend the existing central synchronous predicate to require **Structure AND HistoricalPlan AND Proposal-write AND realization quiescence** before scheduler/snapshot work. Retain publication's existing queue/admission/clocks and Structure rules. A live operation in any participant returns existing busy without epoch advance, capture, staging or writes. If all are quiescent but Proposal/realization is protected, return structured `protected` with its participant ID. If both busy and protected apply, physical nonquiescence takes priority until terminal/owner settlement.

On admitted begin, close ordinary admission and advance epoch before any participant callback can reenter. No ordinary write begins from a capture callback. Do not begin then asynchronously drain old operations behind closed admission. No caller automatically retries destructive replacement. This composition also applies when both realization and publication/Structure are outstanding: settling one does not permit replacement while another remains leased. No cross-owner FIFO or scheduler priority is introduced.

## 10. Initialization, reads, desired state and notifications

Generation-scope Proposal and realization initialization promises. Capture original epoch/generations before open/read, compare after every await and before cache/authority/ingress/protection installation. Also bind protection continuations to the exact protection instance; a later protection is not interchangeable merely because generation matches. Stale read/init returns explicit `contextReplaced`/unavailable, not a valid empty result or new protection on the replacement. Synchronous list methods return only settled authority; protective read models must consult ingress and cannot relabel preserved prior facts as current complete evidence.

Do not let a lazily constructed surface load/adopt old storage after its shell has been installed by replacement. Pending lazy construction must initialize against the current shell snapshot/generation or be discarded; old callers retain their old tokens. Bootstrap/recovery ordering remains Proposal first, realization second. No init-triggered realization or realization retry exists or is added.

Realization has **no legacy pending overlay/desired candidate replay**. Known failure leaves acceptance as the retryable authority; fresh explicit invocation reconstructs the same deterministic facts from those accepted bytes with a new attempt time. Possibly committed attempts remain protected evidence. Proposal's existing exact desired persistence is separate: lifetime-bound, no newly allocated acceptance/automatic callback on persistence retry, no replay of displaced or unconfirmed desired images. A known-failed desired-image retry captures that exact current desired version, verifies its complete write, and installs that image under the Proposal lease; it does not rerun semantic acceptance or allocate new IDs. A later explicit semantic command that supersedes desired state invalidates older desired-retry closures even within the same replacement generation. Abort-restored known-failed desired data is retryable only by a fresh explicit command after current validation.

Deferred notifications capture lifetime and exact installed/evidence instance. They may notify only matching current authority; publication/Preview freshness invalidation caused by old realization cannot fire after replacement. Settlement emits current notifications under the lease and records its own completion then. Subscription exceptions do not cause semantic retry. No polling, durable token, per-render clock sampling or transient exception-based readiness unlock.

Startup must still preserve and protect orphan/incomplete/unresolvable evidence. Do not delete orphan rows, invent acceptance, loosen validators, pretend protected authority is empty or classify historical user data as caused by this race. A fresh verified startup of a fully committed valid set may establish current readiness and later `alreadyRealized`; that is actual durable validation, not an in-session retry through uncertainty.
