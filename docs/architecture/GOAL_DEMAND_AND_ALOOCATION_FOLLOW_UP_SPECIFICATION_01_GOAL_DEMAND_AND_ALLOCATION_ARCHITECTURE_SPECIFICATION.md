# Goal Demand and Allocation Follow-Up Specification 01 — Goal Demand and Allocation Architecture Specification

## Status

Ready for specification.

## Phase

Post-Phase 7 Architectural Follow-Up

## Task Type

Authoritative architecture-specification task converting the completed Goal Demand and Allocation Architecture Audit into a formal DayFrame contract for Goal Demand, Goal-Specific Feasibility, Competing Demand, Allocation, and Accepted Allocation. This task must define how Goals request planning resources from Capacity without becoming Commitments; how authored planning intent becomes deterministic demand projection; how demand provenance, lifecycle, priority, cadence, effort, and feasibility are represented architecturally; how multiple Goal Demands compete for finite Capacity; how provisional Allocation reasons deterministically and explainably without becoming authority; and how explicit user acceptance creates time-owning Goal-driven planning intent.

This task must preserve the committed Capacity architecture and establish the complete downstream contract required before constructive Proposal architecture can be specified.

It may inspect the repository and run focused existing tests where necessary to verify compatibility, but it must not implement Goal Demand, Goal priority, Capacity, feasibility, Allocation, Accepted Allocation, Proposal, scheduling changes, persistence changes, UI, or tests. It must not modify existing architecture documents or assign this work to a future implementation phase.

This task is read-only with respect to the existing repository.

**The required specification result artifact is the sole permitted repository write.**

---

## 1. Objective

Produce the authoritative architecture specification for **Goal Demand and Allocation** in DayFrame.

The completed Goal Demand and Allocation Architecture Audit established:

* **Goal Demand: GD5 — Not Implemented**
* **Goal-Specific Feasibility: GF4 — Reusable Placement Primitives Only**
* **Allocation: AL4 — Analogous Commitment-Ordering Primitives Only**
* **Accepted Allocation: AA4 — Conceptually Related Infrastructure Only**

It identified the first exact break in the intended constructive planning lifecycle immediately after Goal outcome intent:

> **Current DayFrame has no distinct authorized Goal Demand describing what planning resource a Goal requests from Capacity.**

The audit recommended:

> **Path B — Goal Demand and Allocation Architecture Specification**

because Goal Demand and Allocation are mutually constraining around:

* resource-request semantics;
* demand granularity;
* authored versus derived facts;
* Goal priority;
* partial satisfaction;
* feasibility;
* competition;
* allocation policy;
* provenance;
* recurring authority scope;
* and the transition into Proposal and user acceptance.

This specification must resolve those boundaries sufficiently that a later constructive Proposal specification can consume them without reopening foundational Goal-demand or allocation semantics.

## 2. Architectural Context

The committed planning architecture is:

**Commitments + Constraints
→ Capacity
→ Goal Demand
→ Goal-Specific Feasibility
→ Competing Demand
→ Allocation Reasoning
→ Proposal
→ User Decision
→ Accepted Allocation
→ Scheduled Work
→ Execution
→ Progress
→ Summary**

The specification must preserve:

> **Commitments own time. Goals compete for Capacity. DayFrame proposes. The user decides. DayFrame schedules what the user has authorized.**

It must also preserve:

> **Capacity describes what planning resources exist. Goal Demand describes what a Goal requests from those resources.**

and:

> **Allocation reasons provisionally. Proposal recommends. User acceptance authorizes.**

No part of Goal Demand or Allocation may silently promote engine reasoning into authored scheduling authority.

### Derived Demand Projection

> **Derived projection may interpret authorized intent. It may not invent deserved effort.**

## 14. Existing Goal-Linked Commitment Accounting

Resolve the audit's double-claiming concern.

Current Goals may link to independently authored Commitments that already own time.

The specification must define how Goal Demand treats effort already represented by such Commitments.

At minimum evaluate:

### Model A — Linked Commitment Automatically Satisfies Demand

Potentially too strong if linkage is provenance only.

### Model B — Linked Commitment Never Counts

Risk of double scheduling.

### Model C — Explicit Demand-Satisfaction Attribution

The demand explicitly identifies which existing time-owning sources satisfy some or all requested effort.

### Model D — Derived Attribution Under Explicit Policy

DayFrame may calculate satisfaction from linked scheduled/executed work under a declared policy.

Choose a normative model or bounded combination.

Preserve the distinction between:

* planning-demand satisfaction;
* scheduled effort;
* execution;
* Goal Progress.

Do not equate scheduled time with outcome progress.

## 19. Goal-Specific Feasibility Definition

> **Goal-Specific Feasibility is a deterministic, non-authoritative evaluation of one explicit Goal Demand projection against current allocatable Capacity, producing compatible opportunities and unsatisfied-demand information without mutating Capacity, comparing Goals, allocating resources, recommending action, or scheduling work.**
