# Publication Lifecycle & Replacement Isolation Contract V1

**PROPOSED — AWAITING ARCHITECTURAL ACCEPTANCE — NOT IMPLEMENTED**

Task 9.29.1 proposes this contract for architectural review. It does not adopt it, repair production code, or authorize the Task 9.29 interface continuation. Task 9.29 remains PARTIAL/BLOCKED. The accepted, bounded Structure repair in 9.27.2 and the accepted 9.28 work remain unchanged.

## 1. Decision and guarantee boundary

Extend the existing authority transaction with HistoricalPlan quiescence, and extend the existing HistoricalPlan owner with origin tokens, a serial execution queue, and one active publication settlement lease. Capture origin identity synchronously at command entry. Waiting intent is replaceable; executing owner work reserves the right to finish. Replacement must either begin before that reservation or return busy before capturing any snapshot. A physical transaction must reach an observed terminal state before its reservation can be released. Verification, owner adoption, and result recording belong inside the reservation.

This is one ordering policy, not an implementation menu. There is no new publication owner, global lock, journal, or restore engine. Scope is one live JavaScript realm, its registered DayFrame store/HistoricalPlan owner, and writes routed through that composition's adapters. It does not coordinate another tab, another concurrently constructed store over the same database, another process/device, or raw out-of-contract database writes. Tests may construct an independent reader after settlement/replacement to inspect persistence; that is not multi-writer safety.

Successful replacement must leave its intended HistoricalPlan authority intact. Displaced work must not subsequently write, add overlays, adopt metadata, reopen readiness, emit a misleading notification, update the current last-result slot, or flush retries. A publication that settles first is legitimate; subsequent replacement applies its usual semantics to it. Identical restored content and reused batch/source IDs do not preserve an old operation's lifetime. Failed replacement preserves appropriate data/drafts, not permission to replay a prior command.

## 2. Observed foundation and diagnosis

The current public `dayFrameStore.publishScheduleRange` awaits a dynamic import before entering `schedulePublication`. The publisher captures capacity authority, awaits the canonical Review query, checks shared eligibility and the reviewed fingerprint, materializes the exact requested range with `input.publishedAt`, then calls `historicalPlan.publishAtomically`. The owner serializes publication calls, performs initialization/deduplication/collection checks, writes the complete batch, verifies it, adopts metadata, and reports a result. Its source-currentness callback precedes `storage.mutate` but is not supplied as that adapter's physical admission callback.

The adapter can await database opening. Its existing synchronous `admit` callback, when supplied, runs after opening and immediately before transaction creation and request enqueueing. HistoricalPlan does not currently use it. Structure's accepted repair does; Structure also participates in the controller's before-snapshot quiescence predicate. HistoricalPlan does not. Invalidating a promise or changing the epoch does not abort a transaction already created.

Copied, unchanged 9.29 diagnostics passed again under fake IndexedDB: canonical Review was eligible; the actual publication paused before delegation to the real mutation adapter; actual full clear or actual V14 restore succeeded; history was empty before release; then the old command returned `published` and its exact batch survived reinitialization. In each case `physicalAdmissionSupplied` was false and authority epoch advanced from 0 to 1. These tests assert the defect, not this proposed contract. The earlier pause before lazy dispatch failed materialization because Sleep became incomplete; that rejected hypothesis is distinct from the confirmed later race. Neither experiment establishes native-browser reproduction or real-user incidence.

Current-path inventory and source provenance are in the separate execution RESULT and its evidence. All normative language below is proposed behavior.

## 3. Runtime identities and APIs

Use the existing monotonically advancing authority epoch. Add a monotonically advancing HistoricalPlan owner generation and opaque operation identity. Neither is persisted, exported, restored, or copied from runtime snapshots. Runtime installation, clear, protected abandonment, and abort restoration invalidate old generations. An aborted transaction does not roll the epoch or generation back. Each owner instance has a distinct identity even if durable IDs match.

Illustrative runtime-only signatures (names may be made idiomatic without changing these semantics):

```ts
type PublicationOrigin = Readonly<{
  ownerInstance: object;
  operationId: object;
  authorityEpoch: number;
  historicalGeneration: number;
}>;

type ReplacementReadiness =
  | { status: "ready" }
  | { status: "busy"; participant: "historicalPlan" }
  | { status: "protected"; participant: "historicalPlan" };

capturePublicationOrigin(): PublicationOrigin | AdmissionRejection;
isOriginCurrent(origin: PublicationOrigin): boolean;
enqueuePublication(origin, exactCandidate, sourceWitness): Promise<Outcome>;
getHistoricalPlanReplacementReadiness(): ReplacementReadiness;
clearHistoricalPlanForCoordinator(privateCapability, matchingEpoch): Promise<ClearResult>;
```

The store captures origin before its first `await`, including before lazy import. Factory-level `publish`, `publishAtomically`, and explicit retry capture at their own synchronous entry when not given an already captured, owner-validated origin. They must never recapture for an old continuation. The store passes the original origin through the lazy module, query, materializer, owner, and result projection. Origin allocation is not publication acceptance or batch-ID allocation.

Ordinary admission requires externally ready store, inactive authority transaction, current owner instance/epoch/generation, no protected/unavailable owner, and no unresolved physical settlement. Current initialization may be awaited as preparatory work; it confers no right to mutate. A new call during a transaction is rejected as busy. A call whose captured context is displaced is rejected as `contextReplaced`. A busy replacement does not advance epoch or invalidate legitimate current intent.

## 5. Physical admission, terminal receipts, and certainty

Pass the existing `mutate(mutations, admit)` callback. It must synchronously check original epoch, owner instance and generation, the active operation/lease identity, ordinary admission/protection, and the original source witness where explicit publication requires it. No `await`, timer, promise continuation or user callback may intervene between a true check and readwrite transaction creation/request enqueueing. The callback must remain attached through delay wrappers and database opening. Source mismatch yields `sourceChanged`; displaced lifetime yields `contextReplaced`; neither is durable success.

The existing callback alone is insufficient to prove settlement. Add a bounded runtime-only transaction receipt to the collection adapter, with no changes to stored rows or normal caller semantics. For example, an optional internal lifecycle observer may receive `{terminal: Promise<"committed" | "aborted">}` synchronously when the native transaction is created and its terminal handlers are installed, before enqueueing. The owner registers that receipt against the operation. This internal observer must be nonthrowing. `oncomplete` and `onabort` establish terminal state; request error or `onerror` alone does not. The adapter's enqueue-exception path must abort and await terminal settlement instead of returning before abort completes. Adapter-contract tests must cover this path.

The operation's physical attempt also has an admission-open flag. Closing it makes a delayed, not-yet-started delegation fail its callback. If a wrapper loses/throws its response, close that flag and inspect registered receipt state: no started receipt plus the closed callback proves that no later transaction from this attempt can start; a started receipt must be awaited to terminal. This registration and the native admission/create boundary are synchronous within the same realm. Wrappers that discard the callback or create raw transactions violate the adapter contract and are outside this guarantee.

A lease has two release conditions: (1) no live physical transaction and no remaining admitted delegation can start one; (2) owner verification/classification, adoption or protection, and result recording are settled. While a registered transaction remains live, replacement remains busy even if an error has already been reported. There is no timeout that declares it aborted. A terminal observer continues settlement independently of a lost outward acknowledgment. If the native platform never delivers terminal state, keep the fence and protected/unconfirmed feedback; no in-process replacement is authorized. Closing a database connection is not proof of abort. Reload is not a fabricated success: after actual old-realm termination, existing bootstrap/recovery and physical validation determine readiness. Concurrent surviving realms remain outside scope.

A terminal receipt is an exclusion proof, not a substitute for durable verification. Preserve conservative commit-certainty outcomes: acknowledged commit followed by missing/mismatched/unreadable verification is `verificationFailedAfterCommit`; a thrown/lost mutation acknowledgment with possible commit remains `commitStateUncertain`, even if a receipt later proves the transaction terminated. Do not convert either into a new batch or an automatic retry. A proven atomic abort has no new durable batch from that attempt. Pre-admission denial also has no write.

After terminal uncertainty/failure has been classified and protected evidence capture has settled (including a contained capture failure), release the active settlement lease. The owner then reports **protected**, not indefinitely busy. Protection still excludes ordinary publication/retry and ordinary replacement; release does not mean authority is safe. Existing protected-source export/recheck remains available. An unresolved live write instead reports busy for replacement plus protection/unconfirmed outcome for publication. These are distinct conditions.

## 7. Pending work, initialization, reads and notifications

Retain supported legacy `publish(batch)` acceptance/pending behavior. It is exposed by the factory even though no current production caller through DayFrameStore uses it. It is not retired. After known failure, preserve the exact accepted batch ID, timestamp, range, frozen days and pending order. Exact persistence retry does not rematerialize, rereview current setup, advance time, or allocate identity; it retries accepted authority only. The source-currentness callback belongs to fresh explicit publication, not rewriting an already accepted legacy pending batch against today's setup.

A known-not-written pending batch does not hold a permanent lease. Retry captures a fresh origin for that currently authoritative exact pending record, then queues and obtains a lease before its reads/write. Initialization-triggered flush uses a token captured for that initialization lifetime, and joins the queue only after the metadata initialization promise has completed. It must not recursively await the very initialization promise that is awaiting it. It must not bypass queue/admission or recapture identity after replacement. Installed replacement state never automatically revives a displaced flush.

Initialization, metadata reload, ordinary async reads which can trigger `protect`, protected-evidence capture/recheck, and deferred status notifications capture generation/epoch at their start. They do not reserve publication settlement merely by being reads. Recheck after each await before installing state or changing protection. A stale read returns explicit unavailable/context-replaced information; it must not manufacture empty valid history. Stale initialization cannot set ready, clear protection, install metadata or schedule a retry. Cache initialization promises by generation; invalidated promises cannot serve new lifetime callers.

Protection capture also binds to the exact current protection instance. A late evidence read must not replace newer protection evidence. Recheck remains evidence comparison, not authority to reopen ready. Export of protected evidence remains read-only. Deferred notifications carry generation/context and are dropped if stale; synchronous notifications emitted during lease settlement may schedule listeners, but those listeners must check receipts before later effects. Coordinator notifications bind to the newly installed generation.

A successful full clear clears HistoricalPlan pending and metadata only on that owner's confirmed clear success. Successful restore installs its validated target runtime with no displaced pending batches; durable backup rows do not encode pending intent. Exact abort restoration may reinstate the captured pending array, metadata and protection, but under a fresh generation. Old queued retry closures still reject. A new explicit exact retry may act on reinstated known-not-written pending data if current readiness allows it. An uncertain/possibly committed attempt is not an ordinary retryable pending batch; retain its evidence under protection and exclude it from retry. This also applies to legacy retry failure paths.

## 8. Coordinator composition and replacement policy

At **every** controller begin route, before scheduler snapshot/capture or replacement staging, synchronously require both Structure quiescence and HistoricalPlan physical/owner quiescence. Fold HistoricalPlan readiness into the existing controller; do not put an async drain behind `begin`. A nonquiescent owner returns existing busy behavior with participant detail. A quiescent protected HistoricalPlan returns a new runtime structured protected denial (`participant: historicalPlan`), not a misleading busy result. Both deny without snapshot, epoch advancement, staging, or writes.

If ready, close ordinary admission synchronously before invoking any snapshot participant callback, enter the shared transaction and advance epoch; no user callback may obtain ordinary admission during snapshot capture. Snapshot failure reopens appropriate admission after abort handling but keeps the invalidation generation/epoch advanced. This conservative attempted-begin invalidation is deliberate: old intent is not replayed after failed capture. Runtime snapshot data excludes coordination tokens/counters. Preserve the existing scheduler notification protocol.

There is no coordinator-waits-for-publication deadlock: publication reserves while admission is open; replacement checks and returns busy without beginning. Once publication settles, the user can explicitly retry restore/clear. If replacement began first, ordinary publication fails without waiting for admission to reopen. No automatic destructive retry is added.

Existing authorized recovery replacement may bypass ordinary protected readiness only through the current recovery protocol and its validated evidence/source-recheck requirements, **never** physical quiescence. Existing protected abandonment is the separate already-supported explicit operation, not a new automatic repair.

The coordinator's existing capability/epoch callback is the write admission for privileged transactions. Requiring ordinary inactive-transaction admission there would break legitimate restore and is prohibited.

If full clear partially fails after begin, retain its existing per-authority outcomes and correct failed owner state; invalidate old intent regardless. If restore rolls back, exact pre-restore data returns under a new lifetime. If recovery cannot establish authority, retain `authorityRecoveryRequired` readiness and the journal/evidence. No publication or retry is allowed merely because the outer transaction stopped running.

## 9. Identity, time and compatibility

Keep three independent checks: reviewed source validity, operation-lifetime validity, and exact durable publication establishment. The existing capacity fingerprint, canonical Review fingerprint/eligibility and requested range still govern source validity. Owner epoch/generation govern lifetime. Exact metadata and complete-day verification govern durability. Content equality cannot substitute for lifetime; lifetime cannot substitute for Review; terminal transaction status cannot substitute for complete verification.

Preserve `publishedAt` supplied to the command, batch allocation rules, semantic day fingerprints, complete-day atomicity, batch/day ordering and `asOf` precedence including existing tie behavior. Preserve exact frozen source references, incarnations, revisions, timezone/timing and Sleep evidence. Never advance publication time to escape the race or transfer Structure's clock high-water policy. Never reconstruct past history from current setup. Publication, acceptance, realization, Actual and Progress retain distinct meanings.

Recommend **no migration, schema change, or durable version increment**. The mechanism adds only process-local tokens, receipts, queue/lease accounting and runtime result details. It adds no rows, keys, indexes, required serialized fields, new validation restriction on authentic stored data, or new durable states. HistoricalPlan surface/batch V1, supported day V1/V2 and occurrence snapshot V1/V2/V3/V4 semantics, including nested PublishedSleepSnapshot V1, remain readable with their existing legacy coverage distinctions. Current metadata and day rows are verified using the same identity/content rules. The shared database schema remains unchanged.

Current V14 complete backups and all currently supported historical readers remain supported. Durable target/recovery staging and journal formats remain unchanged because epoch/generation/receipts never enter those payloads. Reload derives authority from physical rows and existing recovery, not a saved process token. Existing exact retry/no-op behavior preserves accepted identity while the explicit pending-durability outcome above prevents overstated success. Compatibility acceptance must compare round trips and supported fixtures semantically and structurally, including frozen evidence and unknown-version rejection; identical field names alone are not proof.

No retrospective deletion, normalization, correction, or classifier is authorized. The race offers no reliable way to identify every affected historical batch. Timestamps, missing current Goals, reused IDs or unfamiliar contents are not grounds for removal. Preserve historical evidence, supported readers, raw recovery and every retained capability/module.
